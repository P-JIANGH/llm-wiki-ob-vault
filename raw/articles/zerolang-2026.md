## 1. The Thesis

> "Zerolang is an experimental graph-native programming language where the
> semantic graph is the program database. Humans ask for outcomes. Agents query
> the graph, submit checked edits, and prove the result." — README

The single most important idea: **text is no longer the source of truth for
agents.** In Zero, `zero.graph` is the program. `.0` files are
human-readable **projections** of the graph, generated by the compiler for
review and incidental human editing, not the normal agent write surface.

The agent's primary operations are:
- `zero query <symbol-or-pattern>` — ask the compiler for graph facts
  (functions, call edges, references, node IDs, type facts, capabilities)
- `zero patch --op '<op>'` — submit a checked graph edit; rejected if
  invalid, stale, or shape-violating
- `zero check / test / run` — run only the task validation the task actually needs

## 2. The Editing Loop (graph-first vs text-first)

**Traditional source loop:**
```
agent writes text → check → format → build → inspect failures → (repeat)
```

**Zero graph loop:**
```
agent queries graph → agent submits checked patch
   → compiler rejects invalid graph edits immediately
   → agent runs only task validation → human reviews projection when useful
```

The payoff: a graph patch can target *semantic structure* — "the literal
argument to this write call", "the body of this block", "the function
`main`" — instead of asking an agent to locate and rewrite a span of text.

## 3. The Program Graph (`zero.graph`)

A graph-first package normally contains:
```
zero.toml         # manifest
zero.graph        # checked compiler input (binary store, content-hashed)
src/main.0        # readable projection (review / escape hatch)
```

The graph stores **declarations, types, calls, blocks, imports, capabilities,
and source-map facts directly**. Agents edit those facts with checked
graph patches; humans read `.0` projections when they want a source-like
review view. `zero.graph` is the normal package compile input; `.0` is not.

Each graph-store write records a hash of the source projection inside
`zero.graph` — so drift is detected by content, not by file timestamps.
This is how a freshly cloned or extracted workspace classifies the same
way everywhere.

## 4. Patch Guardrails

Graph patches can include:
- **graph hash expectations** — `--expect-graph-hash graph:abc123` blocks
  stale edits that would overwrite concurrent changes
- **node hash expectations** — locks a specific node from changing under you
- **field expectations** — `expect="hello from zero\n"` checks the current
  value before replacing
- **typed operation names** — `addFunction`, `addParam`, `addReturnBinary`,
  `replaceFunctionBody`, `replaceBlockBody`, `set` (field), `upsertFunction`
- **dry-run and check-only modes** — `--check-only` and `--dry-run` for safe
  preview

The agent-facing contract: write checked semantic edits, not hopeful
text diffs. A patch that would leave a sparse argument list, a missing
expression, a stale graph hash, or an invalid store fails **before** the
package becomes the new compiler input.

## 5. Compile Path (graph-first pipeline)

Parse-first pipeline (most languages): `source → lex → parse → AST → name
resolution → type check → IR → optimization → codegen → artifact`.

Zero's graph-first package path: `zero.graph → repository graph tables →
semantic validation → type checking → MIR and backend facts → direct
codegen → artifact`. Fewer stages, no reparse on the normal path; the
graph is loaded directly.

Long-term direction: memory-map final compiler IR; codegen from semantic
data with as little redundant parsing and reconstruction as possible.
This is *also* how the runtime goals (low memory, fast startup, small
artifacts, explicit capabilities, pay-as-used stdlib) are achieved — not
only an agent-ergonomics argument.

## 6. The Projection Boundary (no silent divergence)

Commands for keeping the graph and its projection in sync:
- `zero export` — write `.0` from the graph (human review)
- `zero import` — read edited `.0` back into the graph (human escape hatch)
- `zero verify-projection` — no-write drift check (CI)
- `zero status` — reports `clean / missing / stale / conflicting /
  unavailable`

`zero status` uses content hashes (not file timestamps) to decide which
side moved. When both sides were edited independently, the command fails
with `RGP006` and offers `zero import` / `zero export` as repairs — it
never picks a side silently. Set `ZERO_STALE=fail` to escalate the
auto-refresh into an `RGP008` failure.

The rule: agents write the graph by default; humans review projections
by choice; humans may edit projections as an escape hatch; `zero import`
reconstructs the graph; `zero verify-projection` catches drift instead
of hiding it.

## 7. CLI Surface (graph-first agent work)

Core commands (defaults to current directory):
```
zero init [--template cli|package] [--manifest toml] [--format binary]
zero query [--fn <name>] [--find <substr>] [--refs <name>] [--calls <name>]
zero view --fn <name>          # one function instead of whole file
zero patch --op '<op>'         # surgical to bulk edits
zero check
zero test
zero run -- <args>
zero build --emit exe|obj|llvm-ir --target <target> --out <path>
zero diff                      # graph diff
zero inspect --json            # machine-readable facts
zero size --json               # artifact size facts
zero mem --json                # memory budget facts
zero targets --json            # targetToolchains, hosted capability facts
zero doctor --json             # host + toolchain readiness
zero skills [get <name>]       # version-matched bundled skills
zero explain <diagnostic-code> # typed diagnostic explanations
zero fix --plan                # typed fix plans
```

Patch operations cover everything from surgical in-function text edits
(`--replace-in-fn <fn> --old <text> --new <text>`, Edit semantics) to
complete helper creation (`upsertFunction ... end`) and whole function
bodies (`--replace-fn <fn> --body-file -` with a heredoc).

`zero inspect --json` exposes: node IDs, graph hashes,
`interfaceFingerprints`, `targetToolchains`, `usedStdlibHelpers`,
`memoryBudgets`, `releaseTargetContract`. Use plain text by default;
`--json` only for automation, exact spans, contracts, or machine-readable
diagnostics.

## 8. Language Surface (highlights)

- **Functions:** `fn add(x: i32, y: i32) -> i32 { return x + y }`
- **Fallible functions:** use `raises` and `check` — no hidden exceptions
  ```zero
  fn requirePositive(value: i32) -> i32 raises [Invalid] {
      if value > 0 { return value }
      raise Invalid
  }
  ```
- **Public declarations** should carry explicit types so graph facts,
  diagnostics, docs, and repair plans stay stable
- **Capabilities:** programs receive capabilities explicitly (e.g.
  `world: World`) — no ambient global runtime access. The stdlib
  documents effects and target support per helper.
- **Blocks as graph nodes:** `while`, `match`, `if/else` all lower to
  explicit graph control-flow nodes. Agents can patch a whole function
  body or a specific block body (`replaceBlockBody #block_then_1234 ...`).
- **Compile-time facts:** a small metadata surface for target and type
  facts (integer/Bool/enum static values, `compileTime`,
  `target.pointerWidth`, `fieldType`, `hasEnumCase`). Invalid queries
  return `MET001` diagnostics. Design goal: explicit graph metadata, not
  runtime registries or raw token-string builders.
- **Modules:** `src/foo.0` defines module `foo`; `src/foo/mod.0`
  defines directory module `foo`. Import cycles and duplicate public
  exports are diagnosed before build output.
- **Targets (8):** `darwin-arm64`, `darwin-x64`, `linux-arm64`,
  `linux-musl-arm64`, `linux-musl-x64`, `linux-x64`, `win32-arm64.exe`,
  `win32-x64.exe`.

## 9. Runtime Goals (non-negotiable)

The graph-first model should reduce agent guessing **without** relaxing:
- token-efficient inspection
- low memory usage
- fast startup and builds
- low runtime latency
- explicit capabilities
- small, dependency-free artifacts

These are inspectable per-graph-input via `zero size --json`,
`zero mem --json`, and the benchmark docs.

## 10. Version-Matched Skills (key agent-facing pattern)

The thin external `vercel-labs/zerolang` skill is a discovery stub only.
The compiler bundles version-matched skills (the canonical reference for
that exact binary):

```sh
zero skills
zero skills get agent       # ~4 KB — read-edit-verify loop
zero skills get language    # ~6 KB — syntax, types, effects, control flow
zero skills get graph       # ~9 KB — zero.graph store, query/view, patch ops
zero skills get diagnostics # ~4 KB — diagnostics, zero explain, fix plans
zero skills get packages    # ~5 KB — manifests, package layout
zero skills get builds      # ~5 KB — build/run, targets, profiles
zero skills get testing     # ~3 KB — test blocks, filters
zero skills get stdlib      # ~39 KB — full signature reference
zero skills get stdlib --topic std.time   # one section only
```

The rule: **fetch each topic at most once per session** — content is
fixed for a given compiler binary, so refetching returns the same text.
If multiple Zero binaries exist, use the one that will run the project.

## 11. Things Intentionally Not Hidden

- hidden method registries
- vtables
- reflection
- ambient heap allocation
- process-global cleanup lists

When a program uses owned resources, allocator state, hosted I/O, network
capability, or C interop, those facts should be visible through graph
inspection and diagnostics.

## 12. Boundaries / Safety

> "Zerolang is experimental. Expect breaking changes, rough edges, and
> security issues. Run it in isolated workspaces, not against production
> systems or sensitive data." — README, AGENTS.md

The contributor policy (AGENTS.md) is explicit: **do not preserve legacy
behavior by default**. Prefer the clearer agent-facing design over
compatibility shims, migration layers, or carrying old paths forward.
This is a pre-1.0 experiment in being agent-first.

## 15. Why This Matters for the Wiki

The wiki's domain is **Agentic System Design**. Zerolang is the most
direct attempt so far to redesign the *programming language itself*
around the agent's edit surface. The cross-references that matter:

- **Read-edit-verify loops** — see `[[concepts/agent-loop-architecture]]`,
  `[[entities/12-factor-agents]]` (Factor 5: own your context window;
  Factor 9: compact errors), `[[entities/pi-coding-agent]]` (7 tools,
  4 modes — analogous split between read-only / write ops)
- **Context engineering for code** — see `[[concepts/context-engineering]]`.
  Zero's `zero query` is exactly the "pre-fetch vs ask" pattern from
  12-Factor Factor 13.
- **The `replace` problem** — text-edit failure modes listed in
  `semantic-vs-text.md` (wrong overload, lost import, format-induced span
  shift, stale file contents) are the same failure modes that motivate
  the prompt caching and structured-output work in the wider agent
  ecosystem.
- **Graph-first vs text-first** — pairs naturally with LangGraph's
  graph-of-nodes-and-edges runtime model (`[[entities/langgraph]]`),
  but at a different layer: LangGraph graphs the *agent's* state
  machine; Zerolang graphs the *program being authored*.
